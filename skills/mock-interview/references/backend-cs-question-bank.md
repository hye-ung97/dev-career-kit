# 백엔드 CS·기초 질문은행

이 파일은 이력서·JD 기반 질문을 모두 마친 뒤 진행하는 마지막 CS 구간에서만 읽는다. 순수 CS뿐 아니라 경력 1~3년 Java/Spring 백엔드 개발자에게 요구되는 프레임워크·데이터 접근 기본기도 포함한다.

## 선택 규칙

1. 30분 면접은 개념 1개를 골라 기본 질문과 적용형 꼬리질문을 하나씩 묻는다.
2. 1시간 면접은 서로 다른 영역에서 개념 2개를 골라 총 3~4문제를 묻는다.
3. JD와 기술 스택에 맞고, 앞선 이력서 질문에서 충분히 검증되지 않은 개념을 우선한다.
4. Java/Spring/JPA를 사용하지 않는 지원자에게는 해당 프레임워크 전용 질문을 묻지 않는다.
5. 질문 문구는 예시다. 지원자의 경력과 앞선 답변에 맞춰 자연스럽게 바꾼다.
6. 평가 신호는 채점의 앵커이지 필수 키워드 목록이 아니다. 표현이 달라도 원리와 인과가 맞으면 인정한다.
7. 기본 질문에 답하지 못했으면 지나치게 어려운 꼬리질문으로 몰아붙이지 않는다. 한계를 기록하고 같은 영역의 더 기초적인 확인 질문으로 바꿀 수 있다.
8. 카드에 **대체 적용형 꼬리질문**이 있으면 기본 질문 뒤 적용형과 대체 적용형 중 하나만 고른다. 둘을 모두 물어 한 개념당 2문제 제한을 넘기지 않는다.
9. **심화 꼬리질문은 심화 모드에서만, 그것도 조건부로 쓴다.** 지원자가 기본 질문과 적용형 꼬리질문을 **모두 정확히 방어했을 때만** 한 번 더 던져 개념당 최대 3문제로 간다. 워밍업·표준 모드에서는 쓰지 않고, 앞 두 질문에서 흔들린 개념에도 쓰지 않는다(몰아붙이는 게 목적이 아니라 상한을 확인하는 게 목적이다).
10. 심화 꼬리질문은 대부분 **실패 조건·운영 판단(L4~L5)**을 묻는다. 정답을 못 맞혀도 감점 폭을 크게 두지 말고, **어디까지 추론했는지**를 기록한다.

## 정확성 원칙

- Gyoogle 자료는 면접 주제를 찾는 목적으로만 사용하고 정답 근거로 사용하지 않는다. 아래 평가 신호는 공식 명세와 제품 문서를 기준으로 유지한다.
- DB, 프레임워크, NoSQL처럼 구현에 따라 동작이 달라지는 주제는 제품·버전·설정을 확인한 뒤 평가한다. 특정 구현의 동작을 전체 기술의 보편 규칙처럼 단정하지 않는다.
- `NoSQL은 스키마나 트랜잭션이 없다`, `외래 키를 만들면 인덱스도 항상 생긴다`, `JWT는 곧 무상태 인증이다` 같은 과도한 일반화를 정답으로 인정하지 않는다.
- 지원자가 평가 신호와 다른 동작을 말했지만 사용한 제품이나 설정에서는 맞을 가능성이 있으면, 반박부터 하지 말고 환경과 근거를 확인한다.

## 난이도 조정

- **경력 1년 미만**: 정의, 목적, 간단한 코드나 상황에서의 동작을 확인한다.
- **경력 1~3년**: 내부 원리, 실패 사례, 대안과 트레이드오프까지 확인한다.
- **JD 특화**: 금융·결제는 정합성·멱등성·동시성을, 트래픽 중심 서비스는 캐시·풀·네트워크·쿼리를 우선한다.
- **면접 모드**: 워밍업은 기본 질문 위주로 가볍게, 표준은 기본 + 적용형, 심화는 잘 방어한 개념에 한해 심화 꼬리질문까지 간다.

## 1. Java·JVM

### JAVA-01 제네릭과 타입 소거

- **기본 질문**: Java 제네릭이 컴파일 타임과 런타임에 각각 어떤 역할을 하나요?
- **적용형 꼬리질문**: 왜 `new T()`나 `List<String> instanceof List<String>` 같은 코드는 허용되지 않을까요?
- **심화 꼬리질문** *(심화 모드 전용)*: 타입 소거가 있는데도 `List<String>`에 `Integer`를 넣는 코드가 대개 막히는 이유는 무엇이며, 그 방어가 무너지는 경로에는 어떤 것이 있을까요?
- **좋은 답변 신호**: 컴파일 타임 타입 안전성, 캐스팅 감소, 타입 소거, 런타임에 구체 타입 정보가 제한됨을 연결한다.
- **아쉬운 답변 신호**: "다양한 타입을 받는다"에서 멈추거나 타입 소거가 모든 런타임 타입 정보를 없앤다고 과도하게 일반화한다.

### JAVA-02 String 불변성과 String Pool

- **기본 질문**: 문자열 리터럴 두 개가 같은 객체를 가리킬 수 있는 이유와 `new String()`의 차이를 설명해 주세요.
- **적용형 꼬리질문**: String이 불변이 아니라면 해시 키, 보안 정보, 멀티스레드 환경에서 어떤 문제가 생길까요?
- **심화 꼬리질문** *(심화 모드 전용)*: 같은 값의 문자열이 대량으로 생성되는 서버에서 `intern()`을 광범위하게 쓰면 어떤 부작용을 걱정해야 할까요?
- **좋은 답변 신호**: 리터럴 intern, 객체 동일성 `==`와 값 동등성 `equals`, 불변성이 해시 안정성과 공유 안전성에 주는 이점을 구분한다.
- **아쉬운 답변 신호**: String Pool이 heap과 완전히 별개의 메모리라고 단정하거나 `==`를 문자열 값 비교로 설명한다.

### JAVA-03 equals, hashCode와 HashMap

- **기본 질문**: HashMap의 키 타입에서 `equals()`와 `hashCode()` 규약이 왜 중요한가요?
- **적용형 꼬리질문**: 키 객체를 Map에 넣은 뒤 해시에 사용되는 필드를 변경하면 어떤 문제가 생길 수 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: 해시가 한쪽 버킷으로 심하게 몰리는 키를 외부 입력으로 받는다면 어떤 위험이 있고, 그때 조회 비용은 어떻게 변하나요?
- **좋은 답변 신호**: 같은 객체로 판단되면 같은 해시가 필요하며, 버킷 탐색 후 동등성 비교가 이뤄지고 가변 키는 조회 실패를 만들 수 있음을 설명한다.
- **아쉬운 답변 신호**: 해시 충돌이 절대 발생하지 않는다고 하거나 두 메서드의 역할을 동일하게 설명한다.

### JAVA-04 JVM 메모리와 GC

- **기본 질문**: 요청 처리 중 생성한 객체와 스레드의 지역 변수는 JVM에서 대략 어디에 놓이며 언제 회수되나요?
- **적용형 꼬리질문**: 메모리 누수가 의심되는 서버에서 heap 크기만 늘리는 방식이 왜 근본 해결이 아닐 수 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: GC 로그나 힙 덤프 없이 "메모리 누수 같다"는 말만 있을 때, 진짜 누수와 단순한 할당률 증가를 무엇으로 구분하시겠어요?
- **좋은 답변 신호**: 객체와 참조를 구분하고, GC root 도달 가능성, heap·스택의 역할, 할당률과 정지 시간 또는 누수 원인 분석을 언급한다.
- **아쉬운 답변 신호**: 스코프가 끝나면 즉시 메모리가 삭제된다고 하거나 GC가 모든 자원 누수를 해결한다고 설명한다.

### JAVA-05 스레드풀

- **기본 질문**: 요청마다 새 스레드를 만들지 않고 스레드풀을 사용하는 이유는 무엇인가요?
- **적용형 꼬리질문**: 작업 큐가 무제한이고 처리 속도보다 요청 유입이 빠르면 어떤 일이 생기며 무엇을 관찰해야 하나요?
- **심화 꼬리질문** *(심화 모드 전용)*: 코어 스레드 수·큐 용량·최대 스레드 수를 함께 설정했는데 최대 스레드가 좀처럼 쓰이지 않는 구성이 될 수 있습니다. 왜 그럴 수 있나요?
- **좋은 답변 신호**: 생성 비용, 동시 실행 제한, 큐 적체, 메모리·지연 증가, 거절 정책, CPU-bound와 I/O-bound 차이를 연결한다.
- **아쉬운 답변 신호**: 스레드 수는 많을수록 빠르다고 하거나 큐와 백프레셔를 고려하지 않는다.

## 2. Spring

### SPRING-01 AOP와 프록시 객체

- **기본 질문**: Spring AOP에서 프록시 객체가 필요한 이유와 실제 메서드 호출 흐름을 설명해 주세요.
- **적용형 꼬리질문**: 대상 객체 내부에서 `this.someMethod()`를 호출하면 로깅이나 트랜잭션 advice가 동작하지 않을 수 있는 이유는 무엇인가요?
- **심화 꼬리질문** *(심화 모드 전용)*: JDK 동적 프록시와 CGLIB 중 무엇이 쓰이느냐에 따라 달라지는 제약에는 어떤 것이 있나요?
- **좋은 답변 신호**: 클라이언트 → 프록시 → interceptor/advice → 대상 객체 흐름과 self-invocation이 프록시를 우회한다는 점을 설명한다.
- **아쉬운 답변 신호**: AOP를 단순히 "코드 중복 제거"로만 설명하거나 프록시와 실제 객체를 구분하지 못한다.

### SPRING-02 `@Transactional` 동작 원리와 self-invocation

- **기본 질문**: `@Transactional`이 붙은 메서드가 호출될 때 트랜잭션은 누가 언제 시작하고 종료하나요?
- **적용형 꼬리질문**: 같은 클래스의 비트랜잭션 메서드가 `this`로 `@Transactional` 메서드를 호출했는데 롤백되지 않았습니다. 원인과 우선적인 개선 방향은 무엇인가요?
- **심화 꼬리질문** *(심화 모드 전용)*: `@Transactional`을 `private` 메서드나 `final` 메서드에 붙이면 왜 기대대로 동작하지 않을 수 있나요? 프록시 방식과 연결해 설명해 주세요.
- **좋은 답변 신호**: 프록시, `TransactionInterceptor`, 트랜잭션 매니저, 외부 호출 경계를 설명하고 책임 분리나 빈 분리를 우선 검토한다.
- **아쉬운 답변 신호**: 애너테이션을 읽는 순간 DB가 자동으로 처리한다고 하거나 self-injection과 `AopContext`만을 무조건적인 해법으로 제시한다.

### SPRING-03 전파, 격리, 롤백 규칙

- **기본 질문**: `REQUIRED`와 `REQUIRES_NEW`는 기존 트랜잭션이 있을 때 어떻게 다르게 동작하나요?
- **적용형 꼬리질문**: 주문 저장은 롤백하되 감사 로그는 반드시 남겨야 한다면 트랜잭션 경계를 어떻게 설계하겠습니까?
- **대체 적용형 꼬리질문**: `@Transactional` 메서드 내부에서 `RuntimeException`을 잡고 정상 반환했더니 일부 변경이 커밋됐습니다. 왜 그럴 수 있고 어떻게 처리하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: 감사 로그를 `REQUIRES_NEW`로 분리했더니 부하가 몰릴 때 커넥션이 부족해졌습니다. 왜 그럴 수 있고 무엇을 확인하시겠어요?
- **좋은 답변 신호**: 참여와 일시 중단·새 트랜잭션, 프록시 경계를 통과하는 예외와 롤백 규칙을 설명한다. 대체 질문에서는 예외를 삼키면 interceptor가 정상 반환으로 볼 수 있음을 알고, 기본 설정의 `RuntimeException`·`Error` 롤백과 checked exception 규칙이 설정으로 바뀔 수 있음을 구분한다.
- **아쉬운 답변 신호**: 전파와 DB 격리 수준을 같은 개념으로 설명하거나 `REQUIRES_NEW`를 항상 안전한 해법으로 본다. 모든 예외가 설정과 무관하게 자동 롤백된다고 단정하거나, 예외를 잡은 뒤 로그만 남겨도 롤백된다고 답한다.

### SPRING-04 IoC/DI와 Bean 생명주기

- **기본 질문**: 객체를 직접 생성하는 방식과 Spring 컨테이너에서 의존성을 주입받는 방식은 무엇이 다른가요?
- **적용형 꼬리질문**: singleton Bean이 요청별 변경 상태를 필드에 저장하면 어떤 문제가 생길 수 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: singleton 빈에 prototype 빈이나 요청 스코프 빈을 주입하면 어떤 일이 생기며, 어떻게 해결하겠습니까?
- **좋은 답변 신호**: 생성·연결 책임의 분리, 대체 가능성, 테스트 용이성, singleton 공유와 동시성 위험을 설명한다.
- **아쉬운 답변 신호**: DI를 애너테이션 사용법으로만 설명하거나 singleton을 단일 스레드 객체로 오해한다.

## 3. 데이터베이스·트랜잭션

### DB-01 격리 수준과 이상 현상

- **기본 질문**: Dirty Read, Non-repeatable Read, Phantom Read의 차이를 예로 설명해 주세요.
- **적용형 꼬리질문**: 격리 수준을 높이면 모든 동시성 문제가 해결될까요? 성능과 충돌 관점에서 설명해 주세요.
- **심화 꼬리질문** *(심화 모드 전용)*: 같은 SERIALIZABLE이라도 잠금 기반 구현과 스냅샷 기반 구현에서 애플리케이션이 준비해야 할 것이 어떻게 달라지나요?
- **좋은 답변 신호**: 읽는 값과 결과 행 집합의 변화를 구분하고, DB 구현 차이, 대기·충돌·재시도 비용을 인식한다.
- **아쉬운 답변 신호**: 격리 수준 이름만 나열하거나 높은 단계일수록 항상 정답이라고 단정한다.

### DB-02 비관적 락, 낙관적 락, 원자적 업데이트

- **기본 질문**: 비관적 락과 낙관적 락은 충돌을 언제 감지하며 각각 어떤 상황에 적합한가요?
- **적용형 꼬리질문**: 재고를 1 감소시키는 기능에서 `UPDATE stock SET quantity = quantity - 1 WHERE id = ? AND quantity > 0`은 어떤 장점과 한계가 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: 낙관적 락 충돌이 잦아 재시도가 늘어나면 어떤 2차 문제가 생길 수 있고, 언제 비관적 락이나 직렬화 처리로 전환을 판단하겠습니까?
- **좋은 답변 신호**: 선점·대기와 버전 충돌·재시도 차이, DB의 단일 원자적 갱신, 복잡한 검증이나 여러 행 정합성에서의 한계를 설명한다.
- **아쉬운 답변 신호**: 원자적 업데이트를 "원자적 락"이라고 부르거나 낙관적 락은 충돌이 없다고 설명한다.

### DB-03 데드락

- **기본 질문**: 두 트랜잭션 사이에 데드락이 발생하는 간단한 예를 들어 주세요.
- **적용형 꼬리질문**: 운영 환경에서 데드락을 줄이고 발생 후 안전하게 복구하려면 어떻게 하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: 특정 행을 직접 갱신하지 않았는데도 데드락이 발생할 수 있습니다. 어떤 잠금 때문일 수 있으며, 인덱스나 실행 계획과는 어떤 관계가 있나요?
- **좋은 답변 신호**: 서로 다른 순서의 락 획득, 짧은 트랜잭션, 일관된 획득 순서, 타임아웃·DB 탐지·제한된 재시도를 말한다.
- **아쉬운 답변 신호**: 락을 쓰지 않는 것만 해법으로 제시하거나 무제한 재시도를 권한다.

### DB-04 인덱스와 실행 계획

- **기본 질문**: 인덱스가 조회를 빠르게 만들면서 쓰기와 저장 공간에는 비용을 만드는 이유는 무엇인가요?
- **적용형 꼬리질문**: `(user_id, created_at)` 복합 인덱스가 있는데 `created_at`만으로 조회하면 기대만큼 사용되지 않을 수 있는 이유는 무엇인가요?
- **대체 적용형 꼬리질문**: `orders.member_id`에 외래 키를 선언했습니다. JOIN이 잦다면 인덱스도 자동으로 생긴다고 봐도 될까요? 인덱스 추가 여부를 어떻게 판단하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: 어제까지 인덱스를 잘 타던 쿼리가 오늘 갑자기 풀스캔으로 바뀌었습니다. 어떤 가능성을 어떤 순서로 확인하시겠어요?
- **좋은 답변 신호**: 탐색 범위 축소, 정렬된 구조, 유지 비용, 선택도, 복합 인덱스 선두 컬럼과 실행 계획 확인을 언급한다. 외래 키의 인덱스 자동 생성 여부는 DB와 참조 방향에 따라 다르며, PostgreSQL은 참조하는 쪽 컬럼의 인덱스를 자동 생성하지 않으므로 쿼리·갱신 패턴과 실행 계획으로 판단해야 함을 안다.
- **아쉬운 답변 신호**: 인덱스가 항상 사용되거나 많을수록 좋다고 답한다. 모든 DB에서 외래 키 선언만으로 양쪽 인덱스가 자동 생성된다고 단정한다.

### DB-05 커넥션풀

- **기본 질문**: DB 커넥션풀을 사용하는 이유와 풀 크기를 지나치게 키웠을 때의 문제를 설명해 주세요.
- **적용형 꼬리질문**: 요청 스레드가 200개인데 DB 커넥션은 20개이고 느린 쿼리가 늘었습니다. 어떤 지표를 보고 어디부터 확인하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: 풀 크기를 늘렸더니 오히려 p99가 나빠졌습니다. 어떤 경로로 그런 일이 생길 수 있나요?
- **좋은 답변 신호**: 연결 생성 비용, DB 동시 처리 한계, 대기 시간, active·idle·pending, connection timeout, 쿼리 시간, 트랜잭션 길이를 연결한다.
- **아쉬운 답변 신호**: 요청 스레드 수와 커넥션 수를 반드시 같게 해야 한다고 답하거나 풀 확대만 제시한다.

### DB-06 키와 제약조건

- **기본 질문**: Primary Key, Unique Constraint, Foreign Key는 각각 어떤 무결성을 보장하나요?
- **적용형 꼬리질문**: 회원가입 전에 이메일 중복 조회를 하는데도 DB에 `UNIQUE` 제약조건이 필요한 이유는 무엇인가요? 동시에 같은 이메일로 두 요청이 들어오는 상황을 설명해 주세요.
- **심화 꼬리질문** *(심화 모드 전용)*: 유니크 제약 위반 예외를 잡아 "이미 존재합니다"로 처리하려 합니다. 이때 진행 중인 트랜잭션 상태와 관련해 무엇을 주의해야 하나요?
- **좋은 답변 신호**: 기본 키의 행 식별과 비NULL·유일성, 고유 제약의 중복 방지, 외래 키의 참조 무결성을 구분한다. 애플리케이션의 사전 조회와 삽입 사이에는 경쟁 조건이 있으므로 DB 제약을 최종 방어선으로 두고, 제약 위반을 애플리케이션에서 처리해야 함을 설명한다. `NULL`의 고유성 처리는 DB 설정과 구현에 따라 확인해야 함을 안다.
- **아쉬운 답변 신호**: 사전 중복 조회만으로 동시 요청까지 완전히 막을 수 있다고 답하거나, 외래 키가 JOIN 결과나 조회 성능을 자동으로 보장한다고 설명한다.

### DB-07 JOIN과 결과 행

- **기본 질문**: `INNER JOIN`과 `LEFT JOIN`은 일치하는 행이 없을 때 결과가 어떻게 달라지나요?
- **적용형 꼬리질문**: `members m LEFT JOIN orders o ON m.id = o.member_id WHERE o.status = 'PAID'`에서 주문이 없는 회원이 결과에서 사라지는 이유는 무엇이며, 그런 회원도 남기려면 조건을 어디에 두어야 하나요?
- **대체 적용형 꼬리질문**: 회원 10명을 조회했는데 일대다 관계의 주문을 JOIN하자 37행이 나왔습니다. 이 결과를 그대로 객체 조회와 페이지네이션에 사용하면 어떤 문제가 생길 수 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: 일대다 JOIN 결과에서 `COUNT(*)`와 `COUNT(DISTINCT m.id)`가 다른 값을 냅니다. 페이지네이션의 전체 개수로는 무엇을 써야 하며 그 근거는 무엇인가요?
- **좋은 답변 신호**: 외부 JOIN이 불일치한 오른쪽 행을 `NULL`로 채운다는 점, `WHERE` 조건은 JOIN 뒤 결과를 필터링하므로 `NULL` 확장 행을 제거할 수 있다는 점을 설명한다. 대체 질문에서는 일대다 JOIN의 행 증폭, 부모 중복, count·페이지 경계 왜곡과 별도 조회·2단계 조회 같은 대응을 연결한다.
- **아쉬운 답변 신호**: JOIN 종류를 문법만으로 나열하거나 `LEFT JOIN`이면 뒤의 `WHERE` 조건과 무관하게 왼쪽 행이 항상 남는다고 답한다. `DISTINCT` 하나로 모든 페이지네이션 문제가 해결된다고 단정한다.

### DB-08 정규화, 이상 현상과 반정규화

- **기본 질문**: 데이터 중복이 삽입·수정·삭제 이상 현상을 어떻게 만들 수 있는지 예를 들어 설명해 주세요.
- **적용형 꼬리질문**: 조회를 줄이려고 모든 주문 행에 회원의 현재 등급과 표시 이름을 복사하려 합니다. 언제 이런 반정규화를 선택할 수 있고, 값이 바뀔 때 정합성을 어떻게 관리하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: 반정규화로 복사한 값이 원본과 어긋났는지 어떻게 탐지하시겠어요? 탐지 장치 없이 운영하면 무엇이 문제인가요?
- **좋은 답변 신호**: 함수적 종속성과 중복으로 인한 불일치를 설명하고, 정규화가 중복과 비일관적 종속을 줄인다는 목적을 안다. 반정규화는 측정된 조회 요구와 허용 가능한 stale 범위를 바탕으로 선택하고, 단일 쓰기 경로·이벤트·배치 검증 같은 동기화 전략과 실패 복구를 함께 말한다. 배송지나 당시 가격처럼 의도적인 역사 스냅샷은 현재값 중복과 구분한다.
- **아쉬운 답변 신호**: 정규화는 언제나 더 빠르거나 반정규화는 언제나 나쁘다고 답한다. 복사한 값이 어떻게 갱신되는지와 실패 시 복구를 설명하지 못한다.

### DB-09 SQL Injection과 파라미터 바인딩

- **기본 질문**: 사용자 입력을 문자열로 이어 붙여 SQL을 만들면 왜 SQL Injection이 가능하며, 파라미터 바인딩은 무엇을 다르게 하나요?
- **적용형 꼬리질문**: 사용자가 정렬 기준을 선택하는 동적 `ORDER BY`를 안전하게 구현하려면 어떻게 해야 하나요? 컬럼명도 일반 값처럼 바인딩할 수 있을까요?
- **심화 꼬리질문** *(심화 모드 전용)*: 정렬 컬럼을 allow-list로 제한했더라도, LIKE 검색이나 개수가 가변인 `IN` 절에서는 추가로 무엇을 주의해야 하나요?
- **좋은 답변 신호**: SQL 코드와 데이터의 분리, prepared statement·JPA 바인딩을 설명한다. 일반 bind parameter는 값 자리에 사용하며 테이블·컬럼 같은 식별자에는 그대로 쓸 수 없으므로, 서버가 정한 컬럼·방향 목록에 매핑하는 allow-list와 최소 DB 권한을 제시한다.
- **아쉬운 답변 신호**: 특수문자 제거 또는 수동 이스케이프만 주 방어책으로 제시하거나, ORM을 사용하면 문자열로 만든 native query까지 자동으로 안전하다고 답한다.

## 4. JPA·Hibernate

### JPA-01 영속성 컨텍스트, 변경 감지와 flush

- **기본 질문**: 조회한 엔티티의 필드만 바꿨는데 UPDATE SQL이 나가는 이유를 설명해 주세요.
- **적용형 꼬리질문**: `flush()`와 트랜잭션 `commit()`은 같은 동작인가요? SQL 실행과 최종 확정 시점을 구분해 주세요.
- **심화 꼬리질문** *(심화 모드 전용)*: 자동 flush 때문에 예상보다 이른 시점에 제약조건 위반이나 SQL 오류가 드러날 수 있습니다. 어떤 상황에서 그런가요?
- **좋은 답변 신호**: 관리 상태, 스냅샷 비교, 쓰기 지연과 flush, DB commit의 차이를 설명한다.
- **아쉬운 답변 신호**: setter가 직접 SQL을 호출한다고 설명하거나 flush가 곧 commit이라고 답한다.

### JPA-02 N+1과 fetch 전략

- **기본 질문**: 부모 목록을 한 번 조회했는데 연관 데이터를 접근하며 추가 쿼리가 N번 발생하는 과정을 설명해 주세요.
- **적용형 꼬리질문**: fetch join, EntityGraph, batch fetch 중 무엇을 선택할지 어떤 기준으로 판단하겠습니까?
- **대체 적용형 꼬리질문**: 일대다 컬렉션 fetch join에 `Pageable`을 함께 적용하면 왜 페이지 크기와 결과가 예상과 달라질 수 있으며, 어떤 대안을 검토하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: batch fetch로 N+1을 줄였을 때도 남는 한계는 무엇인가요?
- **좋은 답변 신호**: 지연·즉시 로딩만 바꾸는 것으로 항상 해결되지 않음을 알고, 조회 모양·페이지네이션·중복 행·컬렉션 수·재사용성을 비교한다. 컬렉션 JOIN의 행 증폭과 DB 행 제한의 충돌을 설명하고, Jakarta Persistence 명세상 collection fetch join에 `setFirstResult`·`setMaxResults`를 적용한 효과가 정의되지 않았으므로 provider 동작에 기대지 않으며 ID 페이지 조회 후 연관 데이터 조회, batch fetch, DTO 조회 등을 상황에 맞게 검토한다.
- **아쉬운 답변 신호**: 모든 연관관계를 EAGER로 바꾸면 해결된다고 하거나 실제 SQL 수를 확인하지 않는다. `DISTINCT`만 붙이면 모든 provider에서 안전한 DB 페이지네이션이 보장된다고 답한다.

### JPA-03 지연 로딩과 OSIV

- **기본 질문**: 영속성 컨텍스트가 끝난 뒤 지연 로딩 연관관계에 접근하면 왜 문제가 생길 수 있나요?
- **적용형 꼬리질문**: OSIV를 켜서 해결하는 방식의 장점과 커넥션 점유·쿼리 위치 측면의 단점은 무엇인가요?
- **심화 꼬리질문** *(심화 모드 전용)*: OSIV를 끄기로 했다면, 지연 로딩에 의존하던 컨트롤러·뷰 코드를 어떤 순서로 정리하시겠어요?
- **좋은 답변 신호**: 프록시 초기화와 컨텍스트 범위, 서비스 계층 조회 설계, 트랜잭션 밖 쿼리, 커넥션 점유 가능성을 설명한다.
- **아쉬운 답변 신호**: OSIV가 N+1을 해결한다고 답하거나 지연 로딩을 무조건 나쁜 전략으로 본다.

## 5. HTTP·네트워크

### NET-01 HTTP 안전성, 멱등성과 재시도

- **기본 질문**: HTTP 메서드의 안전성과 멱등성은 무엇이 다르며 GET, PUT, POST는 일반적으로 어떻게 분류되나요?
- **적용형 꼬리질문**: 결제 POST 요청의 응답을 받기 전에 연결이 끊겼습니다. 클라이언트 재시도로 중복 결제를 막으려면 무엇이 필요할까요?
- **심화 꼬리질문** *(심화 모드 전용)*: 멱등 키를 저장소에 기록해 중복을 막을 때, "처리 중" 상태는 어떻게 다루시겠어요? 같은 키로 두 요청이 동시에 들어오면요?
- **좋은 답변 신호**: 읽기 의미와 반복 요청의 서버 상태 효과를 구분하고, 멱등 키·중복 확인·결과 재사용과 원자적 저장을 제시한다.
- **아쉬운 답변 신호**: HTTP 메서드 이름 자체가 비즈니스 멱등성을 자동 보장한다고 답한다.

### NET-02 HTTP 캐시와 조건부 요청

- **기본 질문**: 브라우저나 중간 캐시가 저장한 응답을 언제 재사용할 수 있는지 `Cache-Control`, ETag 관점에서 설명해 주세요.
- **적용형 꼬리질문**: 데이터가 변경됐는데 사용자가 오래된 응답을 보는 문제를 어떻게 진단하고 완화하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: 중간 캐시나 CDN이 응답을 사용자별로 잘못 공유하는 사고를 막으려면 무엇을 확인해야 하나요?
- **좋은 답변 신호**: freshness와 validation, `If-None-Match`·304, 캐시 키, private/public, 무효화 비용을 구분한다.
- **아쉬운 답변 신호**: 캐시는 TTL만 설정하면 정합성 문제가 사라진다고 답한다.

### NET-03 TCP 연결, 타임아웃과 연결 재사용

- **기본 질문**: HTTP 요청 하나가 서버에 도달하기 전 DNS, TCP, TLS 단계에서 어떤 비용이 생길 수 있나요?
- **적용형 꼬리질문**: 외부 API 호출 지연이 갑자기 커졌다면 connect timeout과 read timeout, 연결풀 지표를 어떻게 구분해 보겠습니까?
- **대체 적용형 꼬리질문**: TCP 흐름 제어와 혼잡 제어는 각각 무엇이 감당하지 못하는 상황을 막으며, 패킷 손실 때 무분별한 애플리케이션 재시도가 왜 문제를 키울 수 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: read timeout이 났지만 서버는 정상 처리를 마쳤을 수 있습니다. 클라이언트는 이 불확실한 상태를 어떻게 다뤄야 하나요?
- **좋은 답변 신호**: 이름 해석, 연결 수립, TLS 협상, keep-alive·연결 재사용, 연결 대기와 응답 대기를 구분한다. 대체 질문에서는 receiver window를 이용한 수신자 보호와 congestion window 등을 이용한 네트워크 경로 보호를 구분하고, 손실·지연 상황의 동시 재시도가 부하를 증폭할 수 있어 timeout, backoff, jitter, 재시도 한도가 필요함을 설명한다.
- **아쉬운 답변 신호**: 모든 타임아웃을 하나로 취급하거나 keep-alive가 연결을 영원히 유지한다고 답한다. 흐름 제어와 혼잡 제어를 같은 창 크기의 다른 이름으로만 설명한다.

## 6. OS·동시성·캐시

### CONC-01 원자성, 가시성과 경쟁 조건

- **기본 질문**: 여러 스레드가 `count++`를 실행할 때 값이 유실될 수 있는 이유를 원자성과 가시성 관점에서 설명해 주세요.
- **적용형 꼬리질문**: `volatile int count`로 바꾸면 문제가 해결될까요? 아니라면 어떤 선택지가 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: 카운터는 Atomic으로 해결했는데 여러 필드를 함께 일관되게 바꿔야 한다면 어떻게 하시겠어요? Atomic을 여러 개 쓰면 왜 부족한가요?
- **좋은 답변 신호**: read-modify-write가 원자적이지 않음, `volatile`의 가시성·순서 보장과 상호 배제 부재, Atomic 또는 락을 설명한다.
- **아쉬운 답변 신호**: CPU가 한 줄씩 실행하므로 안전하다고 하거나 `volatile`을 뮤텍스로 설명한다.

### CONC-02 뮤텍스와 세마포어

- **기본 질문**: 뮤텍스와 세마포어는 무엇을 보호하거나 제한하며 어떤 차이가 있나요?
- **적용형 꼬리질문**: 외부 API 동시 호출을 최대 10개로 제한하는 경우와 공유 Map 갱신을 보호하는 경우 각각 무엇이 더 적합한가요?
- **심화 꼬리질문** *(심화 모드 전용)*: 서버 인스턴스가 여러 대로 늘어나면 이 제한이 왜 깨지며, 분산 환경에서 같은 제한을 두려면 무엇을 고려해야 하나요?
- **좋은 답변 신호**: 단일 소유 상호 배제와 permit 기반 동시 실행 수 제한을 구분하고, 실제 보호 대상과 임계구역을 명확히 한다.
- **아쉬운 답변 신호**: 둘을 스레드 대기 방식의 이름 차이로만 설명하거나 분산 환경에서도 그대로 공유된다고 본다.

### CONC-03 프로세스, 스레드와 blocking

- **기본 질문**: 프로세스와 스레드의 자원 공유 차이와 context switch 비용을 설명해 주세요.
- **적용형 꼬리질문**: 요청 스레드가 외부 I/O에서 오래 대기하면 서버 처리량에 어떤 일이 생기며 어떤 대안을 검토할 수 있나요?
- **심화 꼬리질문** *(심화 모드 전용)*: blocking I/O를 비동기로 바꿨는데 처리량이 기대만큼 늘지 않았습니다. 어디에 병목이 남아 있을 수 있나요?
- **좋은 답변 신호**: 주소 공간과 스레드별 실행 상태, 스케줄링, blocking에 따른 스레드 점유, 제한된 풀·비동기 I/O·타임아웃을 함께 본다.
- **아쉬운 답변 신호**: 비동기면 항상 새 스레드가 필요 없거나 항상 더 빠르다고 답한다.

### CACHE-01 캐시 전략과 무효화

- **기본 질문**: cache-aside의 읽기와 쓰기 흐름, 그리고 DB와 캐시가 어긋날 수 있는 시점을 설명해 주세요.
- **적용형 꼬리질문**: 인기 키가 만료되는 순간 요청이 몰려 DB가 과부하되는 상황을 어떻게 완화하겠습니까?
- **대체 적용형 꼬리질문**: Redis에서 RDB snapshot이나 AOF를 켰다면 중요한 원본 데이터를 Redis에만 저장해도 될까요? 무엇을 추가로 판단해야 하나요?
- **심화 꼬리질문** *(심화 모드 전용)*: 캐시 삭제와 DB 갱신의 순서에 따라 stale 값이 고착될 수 있습니다. 그런 시나리오를 하나 설명해 주세요.
- **좋은 답변 신호**: TTL과 명시적 무효화, stale 허용 범위, stampede, TTL jitter·요청 병합·락·사전 갱신과 장애 시 우회를 비교한다. 대체 질문에서는 RDB의 시점 snapshot과 AOF의 write log·fsync 정책별 데이터 손실 가능성을 구분하고, persistence 사용만으로 업무의 내구성·백업·복구·복제·정합성 요구가 자동 충족되지는 않으므로 RPO·RTO와 장애 모델을 먼저 판단한다.
- **아쉬운 답변 신호**: Redis 사용 자체가 정합성을 보장한다고 하거나 모든 데이터에 같은 TTL을 권한다. persistence 옵션 하나만 켜면 관계형 DB와 동일한 보장이 생긴다고 단정한다.

## 7. 데이터 저장소 선택·보안

### ARCH-01 RDB와 NoSQL 선택

- **기본 질문**: 주문·결제 데이터와 사용자 활동 로그를 저장할 데이터베이스를 고른다면 어떤 요구사항과 접근 패턴부터 확인하겠습니까?
- **적용형 꼬리질문**: 동료가 "NoSQL은 스키마가 없고 트랜잭션도 지원하지 않으니 정합성이 필요 없는 데이터에만 쓸 수 있다"고 말했습니다. 이 설명의 문제점은 무엇인가요?
- **심화 꼬리질문** *(심화 모드 전용)*: 이미 RDB로 운영 중인 기능 일부를 다른 저장소로 옮긴다면, 두 곳에 함께 쓰는 전환 기간의 정합성을 어떻게 관리하시겠어요?
- **좋은 답변 신호**: 데이터 모델과 관계, 주요 읽기·쓰기 패턴, 트랜잭션과 무결성, 일관성, 지연 시간, 확장·가용성, 운영 복잡도를 먼저 비교한다. NoSQL은 여러 제품군을 묶은 말이며 MongoDB처럼 유연한 스키마에도 검증을 적용하거나 다중 문서 트랜잭션을 지원하는 제품이 있음을 예로 들어 제품별 보장을 확인한다. 한 서비스에서도 요구에 따라 여러 저장소를 조합할 수 있음을 안다.
- **아쉬운 답변 신호**: 관계형 DB는 수평 확장이 불가능하거나 NoSQL은 모두 eventual consistency·schema-less·비트랜잭션이라고 단정한다. 유행이나 처리량 하나만으로 저장소를 선택한다.

### SEC-01 인증·인가와 세션·JWT

- **기본 질문**: 인증과 인가는 무엇이 다르며, 서버 세션과 JWT 기반 토큰을 사용할 때 서버 상태·폐기·보안 측면의 차이는 무엇인가요?
- **적용형 꼬리질문**: 서명된 JWT가 탈취됐거나 사용자가 로그아웃했습니다. 토큰이 만료되기 전의 재사용을 어떻게 제한하고, 검증할 때 어떤 항목을 확인하겠습니까?
- **심화 꼬리질문** *(심화 모드 전용)*: deny-list나 세션 버전으로 토큰을 즉시 폐기하기로 했다면, 원래 얻으려던 무상태의 이점 중 무엇이 남고 무엇이 사라지나요?
- **좋은 답변 신호**: 신원 확인과 자원 접근 허용 결정을 구분한다. JWT는 claim을 전달하는 형식이지 인증 방식이나 무상태성을 자동 보장하는 장치가 아니며, 서명은 위변조 탐지이고 암호화와 다름을 안다. `alg` 허용 목록, 서명, `iss`·`aud`·`exp` 등을 검증하고 짧은 만료, refresh token 회전·폐기, `jti` 기반 deny-list 또는 세션 버전 같은 선택지를 위험과 운영 비용에 맞춰 비교한다.
- **아쉬운 답변 신호**: JWT payload가 Base64URL로 인코딩되어 있으므로 암호화됐다고 답하거나, 클라이언트에서 토큰을 삭제하면 탈취본도 즉시 무효화된다고 본다. 쿠키에 토큰을 두면 `HttpOnly` 하나만으로 CSRF까지 해결된다고 단정한다.
