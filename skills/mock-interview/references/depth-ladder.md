# 깊이 사다리 (Depth Ladder) — 주제별 L3/L4/L5 카드

이 파일은 **1단계(면접 설계)**에서 읽는다. 목적은 하나다 — 면접관이 지원자 답변에 즉흥 반응하다가 **어느 주제에나 붙는 필러 질문**("트래픽 10배 오면요?", "장애 나면요?")으로 개수만 채우는 걸 막는 것.

`question-design-guide.md`가 **"어디를 물을지"(프로젝트·소주제 선정)** 를 준다면, 이 파일은 **"그 주제의 바닥에 뭐가 있는지"(질문 재료)** 를 준다. 설계 단계에서 소주제를 고른 뒤, 그 주제의 카드를 읽어 **L3·L4·L5 재료와 면접관이 제시할 대안을 미리 손에 쥐고** 면접에 들어간다. *어떤 순서·태도로* 파고드는지는 `toss-patterns.md`가 준다.

> ⚠️ 카드의 문장을 그대로 읽지 않는다. 이건 질문 대본이 아니라 **면접관이 알고 있어야 할 지형도**다. 실제 질문은 지원자가 방금 한 말에서 만든다.

## 깊이 레벨 정의 (SKILL.md와 동일)

| 레벨 | 이름 | 묻는 것 | 대표 형태 |
|------|------|---------|-----------|
| **L1** | 사실·경계 | 무엇을 했나, 정확히 어떻게 구성돼 있나 | "그 두 처리는 같은 트랜잭션인가요, API 호출인가요?" |
| **L2** | 선택 근거 | 왜 그것이었나, 대안은, 왜 안 했나 | "왜 A였죠? B는 왜 아니었나요?" |
| **L3** | **내부 기작** | 그게 **왜 그렇게 동작**하나 (한 계층 아래) | "그게 빠른 이유가 뭐죠? 내부에서 무슨 일이 일어나나요?" |
| **L4** | **실패 모드·경계** | **어떤 조건에서 무너지나** (동시성·수치·장애) | "그 가정이 깨지는 건 어떤 상황이죠? 그때 뭐가 먼저 터지나요?" |
| **L5** | 설계 판단 | 제약이 바뀌면 결론이 바뀌나 | "정합성 요구가 지금의 10배라면, 이 설계를 그대로 두시겠어요?" |

**L3와 L4를 가르는 기준:** L3는 *정상 동작*의 이유, L4는 *비정상 동작*의 조건이다. "Redis는 인메모리라 빠릅니다"(L3 답변)에서 멈추면 안 되고, "그 인메모리라는 성질 때문에 무엇이 위험해지나요?"(L4)로 넘어가야 한 주제가 닫힌다.

**L3·L4의 순서:** L3 확인은 생략할 수 없지만, 순서는 두 가지다. 원리를 먼저 묻고 실패로 가거나(경로 A), **지원자의 고유명사·수치가 담긴 구체적 실패 상황**을 먼저 던지고 그 답에서 원리로 내려간다(경로 B, 토스형). 경로 B에서 L3로 내려가 확인하지 못한 L4 답은 방어로 인정하지 않는다. (SKILL.md 🪜 참조)

**카드의 `대안` 줄:** 면접관이 "다른 방법은요?" 대신 **이름을 붙여 제시할 대안**이다. "왜 이걸 안 쓰셨어요?"(L2)나 "꼭 필요한가요? 더 간단히는?"(단순화 요구)의 재료로 쓴다.

**카드의 `약한 답 → 강한 답` 줄:** 면접 **답변**의 깊이를 가늠하는 기준점이다(이력서 첨삭용이 아니다). 지원자 답이 왼쪽에 머물면 오른쪽 방향으로 한 겹 더 묻는다.

## 사다리에 없는 주제를 만났을 때

이력서에는 아래 15개 카드에 없는 주제도 나온다. 그럴 땐 **카드를 지어내지 말고** 아래 생성 원칙으로 L3/L4/L5를 즉석에서 만든다. 애매하면 **모르는 척 단정하지 말고 지원자에게 설명을 시키는 방향**(L3 질문)으로 연다.

- **L3 만들기** — 지원자가 쓴 명사 하나를 골라 "그건 내부에서 어떻게 되죠?"를 붙인다. *그 기술이 제공하는 이득의 출처*를 묻는 게 항상 통한다. ("빠르다 → 무엇을 안 해서 빠른가", "안전하다 → 무엇을 보장해서 안전한가")
- **L4 만들기** — L3에서 나온 **동작의 전제를 깨뜨린다.** 전제는 대개 이 중 하나다: ① 동시에 하나만 온다 ② 항상 성공한다 ③ 데이터/트래픽이 지금 크기다 ④ 응답은 반드시 돌아온다 ⑤ 여러 단계가 함께 성공한다(단계 사이 실패) ⑥ 외부 시스템·클라이언트는 약속대로 움직인다 ⑦ 제때 처리된다(지연). 실패를 처리하는 장치가 있으면 **그 장치마저 실패하면**(2단 실패)까지 간다.
- **L5 만들기** — 요구사항 하나를 극단으로 밀고 "그래도 같은 선택인가"를 묻는다. 도메인 강화(더 중요한 데이터), 인스턴스 증가, 트래픽, 신뢰 경계(클라이언트를 믿지 않는다면) 중 하나를 바꾼다.
- **대안 만들기** — 같은 문제를 푸는 **더 단순한 방법**(DB 제약·원자적 UPDATE·동기 호출)과 **더 무거운 방법**(전용 저장소·메시지 큐·분산 트랜잭션)을 하나씩 떠올려 둔다.

## 1. 캐시 · Redis

- **L3 내부 기작**: 인메모리 + 커맨드를 단일 스레드로 처리해 락 경합이 없다는 점 / 자료구조 선택(String에 JSON 통째 vs Hash 부분 갱신 vs Sorted Set)이 조회·갱신 비용을 바꾼다 / 직렬화 포맷과 payload 크기 비용 / TTL 만료 방식(접근 시 lazy + 백그라운드 active) / `maxmemory-policy`에 따라 무엇이 먼저 쫓겨나는가
- **L4 실패 모드**: cache stampede(동시 미스가 DB로 그대로 통과) / hot key 한 노드 쏠림 / big key·`KEYS`·`HGETALL` 같은 O(N) 커맨드가 이벤트 루프를 붙잡아 **모든 클라이언트가 함께 느려짐** / TTL 동시 만료로 인한 절벽 / 복제가 비동기라 리플리카 읽기에서 read-after-write가 깨짐 / 캐시-DB 이중 쓰기 순서에 따른 stale 고착 / 영속화(RDB fork)나 failover 시점의 지연 튐
- **L5 설계 판단**: 정합성 요구가 올라가면 cache-aside를 유지할지, 무효화 전용으로 갈지, 아예 캐시를 걷을지 / 캐시가 빠지면 서비스가 죽는 구조인가(= 캐시가 가용성 의존 지점이 된 것) / 로컬 캐시 + Redis 2계층의 비용 / 캐시가 아니라 쿼리·스키마가 진짜 문제였던 것 아닌가
- **대안**: 로컬 캐시 / 쿼리·인덱스 개선 / 읽기 복제본 / 용도에 맞는 자료구조(정렬이 필요하면 Sorted Set 등) / Redis 장애 시 DB로 폴백할지 실패시킬지
- **약한 답 → 강한 답**: "`KEYS`를 쓰지 않았다" → "`SCAN`으로 N개씩 나눠 조회하며 속도와 부하의 균형을 맞췄다"

## 2. 인증 · 인가 (JWT · 세션)

- **L3 내부 기작**: 토큰의 세 조각과 **base64url은 인코딩이지 암호화가 아니라는 점** / 서명 생성·검증 절차 / HS256(공유 비밀)과 RS256(개인키 서명·공개키 검증)의 키 배포 차이 / 검증 시 서버가 실제로 확인하는 클레임(`exp`·`nbf`·`iss`·`aud`·`alg`) / 세션 방식은 무엇을 어디에 저장하고 쿠키 속성(HttpOnly·Secure·SameSite)이 무엇을 막는가
- **L4 실패 모드**: 탈취된 토큰을 만료 전에 무효화할 수 없다 → 짧은 만료 + refresh 로테이션 + 재사용 감지 / 블랙리스트를 두는 순간 무상태 이점이 사라진다 / `alg` 혼동·`none` 수용 / 서버 간 시계 오차 / 페이로드에 민감정보를 담음 / 권한을 회수해도 토큰 만료까지 반영 안 됨 / 저장 위치 트레이드오프(localStorage=XSS, 쿠키=CSRF)
- **L5 설계 판단**: 무상태 확장성이 이 규모에서 실제로 필요한가 / 다중 서비스·모바일 클라이언트면 토큰, 단일 웹앱이면 세션이 더 단순 / 인가를 토큰 클레임으로 굳힐지 매 요청 조회할지
- **대안**: 서버 세션 + 공유 세션 저장소 / 불투명(opaque) 토큰 + 조회 / 짧은 만료 액세스 토큰 + refresh 로테이션

## 3. 트랜잭션 · 락 · 동시성 제어

- **L3 내부 기작**: 각 격리 수준이 **어떤 이상 현상을 막는가**(dirty read / non-repeatable read / phantom) / 스냅샷 읽기(MVCC)와 잠금 읽기의 차이 / 락이 행이 아니라 **인덱스에 걸린다**는 점(InnoDB 기준), 그래서 인덱스가 없으면 잠금 범위가 넓어진다 / `SELECT ... FOR UPDATE` 없이도 **UPDATE 문 자체가 대상 행에 쓰기 락을 잡는다**는 점 / 낙관적 락의 판정은 `UPDATE ... WHERE version = ?`의 영향 행 수 / 원자적 조건부 UPDATE(`SET qty = qty - 1 WHERE qty >= 1`)가 왜 별도의 조회-후-갱신 락 없이도 초과 차감을 막는가
- **L4 실패 모드**: 락 획득 순서 역전으로 인한 데드락 / 잠금 대기 타임아웃 → 커넥션 점유 → 풀 고갈의 연쇄 / 롱 트랜잭션이 언두 이력과 복제 지연을 키움 / **트랜잭션 안에서 외부 API를 호출** / 재시도할 때 멱등성이 없어 이중 처리 / 분산 락(Redis)의 TTL이 작업보다 먼저 끝나 두 프로세스가 동시 진입 / 애플리케이션에서 조회 후 조건 검사하고 갱신하는 사이의 경쟁
- **L4 추가**: **잠글 행이 아직 없을 때**(중복 INSERT 방지) `FOR UPDATE`의 동작은 DB·격리 수준·인덱스에 따라 다르다(InnoDB REPEATABLE READ는 갭 락을 걸 수 있지만 데드락 위험이 커지고, READ COMMITTED에서는 갭 락이 대개 걸리지 않는다) → 존재하지 않는 행의 중복은 **유니크 제약**이 확실하다 / 차감 UPDATE는 성공했는데 뒤이은 INSERT가 실패하는 단계 사이 실패
- **L5 설계 판단**: 락으로 막을 문제인가, 유니크 제약·원자적 UPDATE·큐 직렬화로 **경쟁 자체를 없앨** 문제인가 / 정합성을 DB에 맡길지 보상 트랜잭션으로 갈지 / 분산 락이 필요한가, DB 하나로 충분한가
- **대안**: 원자적 조건부 UPDATE / 유니크 제약 / 낙관적 락(version) / 비관적 락(`FOR UPDATE`) / 분산 락 / 큐로 직렬화 / UPDATE와 INSERT의 **순서 뒤집기**
- **약한 답 → 강한 답**: "Redis `SET NX`로 락을 잡았다" → "획득은 `SET key token NX PX ttl` 한 명령으로 원자적으로, 해제는 소유자 토큰을 확인한 뒤 삭제하는 과정을 스크립트로 원자화했고, TTL이 작업보다 먼저 끝나는 경우(펜싱 토큰 등)와 DB 락 대비 장단점까지 따졌다"

## 4. JPA · ORM

- **L3 내부 기작**: 영속성 컨텍스트의 1차 캐시와 **스냅샷 비교 기반 변경 감지** / flush 시점(커밋 직전·JPQL 실행 전·명시 호출)과 쓰기 지연 / 지연 로딩이 프록시로 동작하고 언제 초기화되는가 / 트랜잭션 밖에서 프록시를 건드리면 왜 터지는가
- **L4 실패 모드**: N+1(연관을 순회할 때 쿼리 폭발) / 컬렉션 fetch join + 페이징 시 DB가 아니라 **메모리에서 페이징**됨 / 컬렉션을 둘 이상 fetch join할 때의 곱연산 / OSIV로 뷰 렌더링까지 커넥션을 잡고 있음 / cascade·orphanRemoval 오설정으로 인한 의도치 않은 삭제 / 벌크 연산 후 영속성 컨텍스트가 옛 값을 들고 있음
- **L5 설계 판단**: 이 조회를 ORM으로 풀지, 네이티브 쿼리·조회 전용 모델로 분리할지 / 엔티티 그래프를 얼마나 크게 끌고 갈 것인가
- **대안**: fetch join / 배치 사이즈(IN 조회) / DTO 직접 조회 / 네이티브 쿼리 / 조회 전용 모델 분리

## 5. 인덱스 · 쿼리 튜닝

- **L3 내부 기작**: B+트리의 정렬된 리프와 범위 스캔 / **복합 인덱스의 왼쪽 접두사 규칙** / 카디널리티·선택도가 옵티마이저 선택을 좌우 / 커버링 인덱스로 테이블 접근을 없앰 / 세컨더리 인덱스가 PK를 들고 있어 한 번 더 찾아가는 구조 / 실행 계획은 통계 기반 **추정**이라는 점
- **L4 실패 모드**: 인덱스 컬럼에 함수·연산·암묵적 타입 변환을 걸어 인덱스 미사용 / 선행 와일드카드 LIKE / 선택도가 낮아 옵티마이저가 풀스캔을 고름 / OFFSET이 큰 페이징 / 인덱스를 늘릴수록 쓰기 비용과 잠금 범위 증가 / 통계 갱신 지연으로 어느 날 갑자기 계획이 바뀜 / 정렬·임시 테이블 발생
- **L5 설계 판단**: 인덱스로 풀 문제인가 집계 테이블·비정규화·검색 엔진으로 갈 문제인가 / 읽기 복제본 분리 시 복제 지연을 감당할 수 있나
- **대안**: 복합·커버링 인덱스 / 키셋(커서) 페이징 / 단일 조인 쿼리로 합치기 / 집계 테이블·비정규화 / 캐시 / 검색 엔진

## 6. 커넥션풀 · 스레드풀 · 타임아웃

- **L3 내부 기작**: 풀이 없애주는 비용은 무엇인가(TCP 핸드셰이크 + 인증) / **풀 크기가 곧 그 애플리케이션의 DB 동시성 상한** / 커넥션 획득 대기 타임아웃과 쿼리 타임아웃은 서로 다른 것 / 스레드풀에서 코어·큐·최대 스레드가 상호작용하는 순서(대개 큐가 찬 뒤에야 최대치까지 늘어난다)
- **L4 실패 모드**: 풀 고갈 → 대기가 응답시간에 그대로 더해짐 / 트랜잭션 안 외부 호출이 커넥션 점유 시간을 지배 / 무제한 큐가 지연과 메모리를 동시에 키움 / 타임아웃 미설정으로 스레드가 영구 점유 / 재시도가 부하를 증폭 / 커넥션 누수 / DB `max_connections`를 인스턴스 수 × 풀 크기가 넘어섬
- **L5 설계 판단**: 풀 크기를 무엇으로 산정하는가(코어 수·평균 응답시간·동시 요청) / 백프레셔·서킷 브레이커·격벽으로 장애를 가둘 것인가
- **대안**: 풀 크기 조정 vs 커넥션 점유 시간 단축(트랜잭션 밖으로 외부 호출 빼기) / 타임아웃 세분화 / 격벽(풀 분리) / 비동기 처리
- **사실 고정 질문**: "풀 크기는 정확히 몇 개였죠? 인스턴스는 몇 대였고요? 그 수치는 초당인가요?" — 수치를 바로 대는지가 실제 운영 경험의 신호다

## 7. 메시징 · 비동기 (Kafka · 큐)

- **L3 내부 기작**: 순서가 **파티션 단위로만** 성립한다 / 파티션 키가 분배와 순서를 동시에 결정 / 컨슈머 그룹과 오프셋 커밋 시점이 재처리 범위를 정함 / ack 유실 가능성 때문에 기본 보장이 at-least-once가 되는 이유 / 아웃박스가 "DB 커밋"과 "발행 의도 기록"을 한 트랜잭션으로 묶는 원리, 그리고 그걸 꺼내 발행하는 방식(폴링 워커 vs CDC)
- **L4 실패 모드**: 중복 소비 → **소비자 멱등성이 없으면 그대로 이중 처리** / 오프셋을 먼저 커밋하면 유실, 나중에 커밋하면 중복 / 컨슈머 랙 누적 / 리밸런싱 중 중복·정지 — 그리고 **리밸런싱이 원인이라는 증거**(리밸런스 로그·랙·재시도 지표)를 대지 못하는 RCA / 처리를 다른 스레드(워커 풀)에 넘기는 구조에서 **종료·리밸런스 시 처리 중이던 레코드와 커밋** / 처리 실패 재시도와 DLQ 설계, 재처리를 쉽게 만드는 도구 / DB 커밋과 메시지 발행이 원자적이지 않음(아웃박스 필요) / 아웃박스 워커가 여러 대 뜰 때의 **중복 발행**과 상태 관리 / 발행은 성공했는데 "발행됨" 상태 업데이트가 실패 / 폴링 주기·워커 지연만큼 이벤트가 늦게 나감(사용자 알림 지연) / 특정 키 쏠림으로 한 파티션만 밀림 / 파티션을 늘리기 어려울 때 처리량 한계
- **L5 설계 판단**: 정말 비동기여야 하나(동기 호출 + 재시도로 충분한가) / 순서 보장이 도메인에 필요한가, 필요하다면 그 대가(파티션 수 = 병렬도 상한)를 받을 수 있나 / 실시간성이 중요해지면 폴링을 유지할 것인가
- **대안**: CDC(로그 기반 변경 캡처) / 커밋 후 로컬 이벤트 리스너(커밋 후 발행 전 장애 시 유실 위험) / 동기 호출 + 재시도 / 키 단위 병렬 처리 컨슈머 / 파티션 증설

## 8. HTTP · API 설계

- **L3 내부 기작**: 안전성과 멱등성의 정의, 메서드별 성질 / 상태 코드가 클라이언트·게이트웨이의 재시도 동작을 좌우한다 / 조건부 요청(ETag·If-None-Match)과 캐시 헤더의 역할 / keep-alive로 커넥션을 재사용하는 이유 / connect 타임아웃과 read 타임아웃의 구분
- **L4 실패 모드**: POST 재시도로 인한 중복 생성 → 멱등키 / **타임아웃이 났지만 서버는 성공한 불확실 상태** / 실패를 4xx/5xx로 잘못 분류해 무의미한 재시도 유발 / 백오프·지터 없는 재시도 폭풍 / 동기 호출 체인에서 하나의 지연이 전부로 전파 / 페이지네이션 없는 대용량 응답
- **L5 설계 판단**: 동기 API로 둘지 이벤트로 뺄지 / 클라이언트 계약과 버저닝을 어떻게 끊을지 / 장애 전파를 어느 경계에서 차단할지
- **대안**: 멱등키 헤더 / 같은 생성 API 재호출 vs 상태 조회 API / 비동기 접수(202) + 결과 조회 / 이벤트 발행

## 9. 배포 · 무중단 · 운영

- **L3 내부 기작**: 롤링·블루그린·카나리가 각각 언제 트래픽을 옮기는가 / readiness와 liveness가 서로 다른 것을 판정한다 / graceful shutdown의 순서(신규 인입 차단 → 인플라이트 처리 → 종료)
- **L4 실패 모드**: 배포 중 **구버전과 신버전이 동시에 떠 있는 구간** → DB 스키마 변경을 확장 후 축소(expand-migrate-contract)로 나누지 않으면 한쪽이 깨짐 / 캐시에 남은 구버전 직렬화 포맷 / 되돌릴 수 없는 마이그레이션 / 종료 시그널을 무시해 처리 중 요청 유실 / 스케일아웃 직후 캐시 미스 폭증
- **L5 설계 판단**: 이 변경은 되돌릴 수 있는가(피처 플래그로 분리 가능한가) / 배포 단위와 서비스 경계를 어떻게 맞출 것인가
- **대안**: 롤링 / 블루그린 / 카나리 / 피처 플래그 / expand-migrate-contract

## 10. 모니터링 · 장애 대응

- **L3 내부 기작**: 메트릭·로그·트레이스가 각각 답하는 질문이 다르다 / **평균이 p99를 숨기는 이유**(꼬리 지연) / 요청률·에러율·지연(RED) 또는 사용률·포화·에러(USE) 관점 / 분산 트레이스가 서비스 경계를 넘어 요청을 잇는 방법
- **L4 실패 모드**: 평균만 보다 소수 사용자의 심한 지연을 놓침 / 지표 자체가 없어 원인 규명 불가 / 알람 임계가 잘못돼 무시되거나 폭주 / 증상(응답 느림)과 원인(풀 고갈)을 혼동 / 재현되지 않는 간헐 장애 / 로그에 상관관계 ID가 없어 추적 불가
- **L4 추가**: 시스템 지표는 정상인데 비즈니스가 깨짐(예: 결제 건수가 평소 대비 급감) — 비즈니스 지표를 보지 않으면 못 잡는다 / 처음 세운 탐지 규칙이 오탐·미탐을 내고 개선되지 않음
- **L5 설계 판단**: 무엇을 SLO로 삼을 것인가 / 관측 가능성에 얼마를 투자할 것인가 / 탐지 규칙을 어떤 신호로 개선해 갈 것인가
- **대안**: 시스템 지표 vs 비즈니스 지표 알람 / 로그 기반 vs 메트릭 기반 탐지 / 샘플링 트레이싱
- **관측 근거 질문**: "그 문제는 어떻게 아셨어요? 모니터링이 없었다면 무엇으로 확인했죠?" — 결론이 맞아도 감지·측정 방법을 못 대면 한 번 더 판다

## 11. 대용량 배치 · 데이터 처리

- **L3 내부 기작**: 청크 단위 처리와 커밋 경계 / OFFSET 페이징과 키셋(커서) 페이징의 비용 차이 / 전부 메모리에 올리지 않고 스트리밍하는 방법
- **L4 실패 모드**: 롱 트랜잭션이 락과 언두를 키움 / 중간 실패 시 어디서 재시작하나(체크포인트·멱등성) / 처리 도중 소스 데이터가 변경됨 / 대량 UPDATE가 복제 지연과 잠금 확산을 유발 / 스케줄러 중복 기동으로 이중 실행
- **L5 설계 판단**: 배치로 갈지 스트리밍으로 갈지 / 언제든 재처리 가능한 설계인가
- **대안**: 청크 커밋 / 행별 트랜잭션 / 키셋 페이징 / 스트리밍 처리 / 실행 전 전체 검증 후 일괄 실행

## 12. 서비스 분리 · 서비스 간 통신

- **L3 내부 기작**: 경계가 곧 **데이터 소유권**의 경계다 / 동기 호출 체인에서 지연은 더해지고 가용성은 곱해진다 / 서비스를 나누는 순간 하나의 DB 트랜잭션이 사라진다
- **L4 실패 모드**: 한 서비스의 지연이 호출자의 스레드를 붙잡아 연쇄 장애 / 분산 트랜잭션 부재 → saga·보상 로직과 그 실패 처리 / 데이터 복제로 인한 정합성 지연 / 네트워크 파티션·부분 실패 / 서비스 간 계약 버전 불일치
- **L5 설계 판단**: 정말 나눠야 했나(모듈러 모놀리스로 충분했나) / 경계를 어디에 그을 것인가, 그 경계가 조직 구조와 맞는가
- **대안**: 모듈러 모놀리스 / 같은 DB 트랜잭션으로 묶기 / 동기 API vs 이벤트 / Saga
- **경계 확인 질문**: "그 두 처리는 같은 트랜잭션인가요, 같은 스레드인가요, 서비스 간 API 호출인가요?" — 답이 확정될 때까지 묻는다. 경계가 흐리면 뒤의 정합성 질문이 모두 흔들린다

## 13. 멱등성 · 중복 요청

- **L3 내부 기작**: 멱등 키의 **범위와 생성 주체** — 클라이언트가 요청마다 새 키를 만들면 재시도도 새 요청이 된다 / 키 기록과 비즈니스 변경을 **같은 DB 트랜잭션**에 두는 이유 / 유니크 제약이 같은 키의 동시 INSERT를 어떻게 하나만 성공시키는가(InnoDB·PostgreSQL 기준: 뒤 트랜잭션은 앞 트랜잭션이 끝날 때까지 기다렸다가, 앞이 커밋되면 중복 오류, 롤백되면 성공) / "처리 중"과 "완료" 상태의 구분 / 같은 키 재요청에 이전 결과를 돌려주는 방식
- **L4 실패 모드**: 같은 키로 두 요청이 동시에 들어옴(첫 요청 처리 중) / 키는 기록됐는데 본 처리가 롤백됨 → 재시도가 "이미 처리됨"으로 건너뛰어 유실 / 다른 키로 같은 의도의 요청(더블 클릭, 클라이언트가 키를 다시 만듦) / 키 보관 기간이 재시도 기간보다 짧음 / 응답 유실로 클라이언트가 결과를 모름 / **서로 다른 저장소(캐시와 DB)에 걸친 판정을 하나의 원자 연산으로 착각**(캐시 스크립트는 DB 변경까지 원자화하지 못한다)
- **L5 설계 판단**: 멱등성을 어디서 보장할 것인가 — 클라이언트 구현을 신뢰하지 않는다면 서버에서 / 비즈니스 키(주문번호·이벤트 ID)로 자연 멱등을 만들 수 있나 / 가장 단순한 해법은 **고유 ID + 유니크 제약 + 같은 트랜잭션**인데, 그 이상이 꼭 필요한가
- **대안**: 유니크 제약 / 원자적 조건부 UPDATE / 멱등 키 테이블 / Redis `SET NX` 선점 / 상태 머신 전이 조건(`WHERE status = 'READY'`)

## 14. 분산 정합성 · 외부 연동 (보상 · 대사 · 결과 불명)

- **L3 내부 기작**: 서비스·외부 시스템을 넘는 순간 **하나의 DB 트랜잭션이 사라진다** / 보상 트랜잭션은 롤백이 아니라 **되돌리는 새 작업**이다 / 아웃박스가 "내 커밋"과 "보낼 의도"를 묶는 원리 / 대사(reconciliation)가 무엇을 기준으로 불일치를 찾는가 / **타임아웃은 실패가 아니라 결과 불명**이다
- **L4 실패 모드**: 외부 호출은 성공했는데 우리 DB 커밋이 실패 / 우리 커밋은 됐는데 외부 호출이 타임아웃(결과 불명) / **보상 자체가 실패**(2단 실패) / **트랜잭션 안에서 외부 HTTP 호출** → 커넥션을 오래 점유하고, 외부 쪽은 롤백되지 않는다 / 재시도가 외부에 중복 생성 / 대사 주기 사이의 불일치를 사용자가 먼저 봄 / 외부 데이터 소스와 우리 데이터의 갱신 시점이 어긋남
- **L5 설계 판단**: 정말 원자성이 필요한가(요구 재확인) / 동기 처리 vs 비동기 + 보상 / "결과 불명" 상태를 사용자에게 어떻게 보여줄 것인가 / 선차감 vs 후차감처럼 **순서 결정**이 정합성과 사용자 경험을 어떻게 바꾸는가 / 모든 문제에 메시지 큐·분산 트랜잭션이 필요한가(비용 판단)
- **대안**: Saga(오케스트레이션·코레오그래피) / 아웃박스 / 2PC(대개 비현실적) / 대사 배치 / 상태 조회 API로 결과 확인 / 상태를 하나로 합쳐 단순화

## 15. 장애 격리 · 서킷브레이커 · 폴백

- **L3 내부 기작**: 서킷 상태(닫힘·열림·반열림)와 전이 조건(실패율·느린 호출 비율, 횟수 또는 시간 기반 윈도우) / 실패 집계를 어떤 자료구조로 하는가(링 버퍼·시간 버킷) / 타임아웃·재시도·서킷 중 무엇이 바깥에서 감싸느냐에 따라 재시도가 집계에 어떻게 잡히는지 달라진다 / 폴백이 실제로 무엇을 반환하는가
- **L4 실패 모드**: **인스턴스마다 서킷 상태가 따로**라 같은 외부 장애에 판단이 엇갈림 / 부분 장애(일부 요청만 실패)에서 정상 처리 가능한 요청까지 막음 / 폴백 대상(DB)으로 트래픽이 몰려 연쇄 장애 / 실패가 아니라 **지연**일 때 스레드 고갈 / 재시도 폭풍 / 캐시 장애에 폴백이 없어 전체 장애
- **L5 설계 판단**: 서킷브레이커가 꼭 필요한가(타임아웃 + 재시도로 충분한가) / 상태를 인스턴스 간에 공유할 것인가(공유 저장소가 새 의존점이 된다) / 핵심 데이터라면 장애 시 요청을 통과시킬 것인가(fail-open) 거부할 것인가(fail-closed) — 서킷의 '열림(=차단)'과 뜻이 반대이니 주의 / 격벽으로 자원을 나눌 것인가
- **대안**: 타임아웃 + 재시도 + 백오프 / 헬스 체크 / 격벽 / 레이트 리미터 / 공유 상태 저장소

## 카드 사용 규칙

1. **설계 때 미리 읽는다.** 면접 중에 급하게 찾지 말고, 1단계에서 주제별 사다리를 손에 쥔 채 들어간다.
2. **모드가 필수 도달 레벨을 정한다.** 워밍업=L2, 표준=L3, 심화=L4~L5. (SKILL.md 참조)
3. **지원자가 안 쓴 기술의 카드를 억지로 꺼내지 않는다.** 이력서·JD에 근거가 있는 주제만.
4. **정확성이 최우선.** 카드에 없는 세부를 지어내 단정하지 않는다. 제품·버전·설정에 따라 다른 동작(격리 수준 기본값, 락 구현, 풀 정책 등)은 **지원자가 쓴 환경을 먼저 확인**하고 판단한다.
5. 지원자가 카드의 L4를 스스로 먼저 짚으면 **그건 강한 신호**다. 세션 노트에 그대로 기록하고 L5로 올린다.
6. **카드는 기술 지형도이지 "토스가 이걸 묻는다"는 근거가 아니다.** 실제 면접에서 관찰된 경향은 `toss-patterns.md`에 따로 있다. 13~15번 카드는 실제 토스 계열 면접 기록에서 정합성 관련 질문이 많았던 것을 반영해 추가했지만, 내용 자체는 일반 기술 지식이다.
7. 흔한 키워드(아웃박스·분산 락 등)는 카드의 정의를 묻지 말고 **지원자가 실제로 다룬 범위**(유실·중복을 어디서 어떻게 막았나)부터 묻는다.
