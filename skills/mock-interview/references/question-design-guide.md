# 질문 설계 가이드 (JD 5슬롯 파싱 + PSR 분해 + 트리거)

이 파일은 **1단계(면접 설계)**에서 읽는다. 목적은 하나다 — **질문이 "이력서를 낭독하게 만드는 질문"이 아니라 "그 회사가 실제로 궁금해할 지점"과 "지원자가 실제로 한 일"의 교집합을 정확히 겨누게** 하는 것.

질문 설계는 세 축으로 한다:
1. **JD 5슬롯 파싱** — 채용공고에서 "이 회사가 검증하고 싶은 것"을 5개 슬롯으로 구조화한다.
2. **PSR 분해** — 이력서의 한 줄을 문제·해결·결과로 쪼개 어디를 파고들지 앵커를 잡는다.
3. **트리거 찾기** — 실제 토스 계열 면접 기록에서 꼬리질문의 출발점이 된 이력서 요소(수치 주장·결여·본인 용어·"보장" 문장 등)를 찾아 **프로젝트 × 소주제**로 쪼갠다.

셋을 교차하면, 각 소주제의 **첫 질문(오프너)과 꼬리물기 방향**이 자동으로 나온다.

> **이 파일은 "어디를 물을지"까지만 준다.** "그 주제를 얼마나 아래까지 팔 수 있는지"는 같은 폴더의 `depth-ladder.md`가 준다. 주제를 고른 뒤 그 파일을 반드시 함께 읽는다 — 둘 중 하나만 하면 *겨냥은 정확한데 얕은* 면접이 되거나, *깊긴 한데 엉뚱한 데를 파는* 면접이 된다.

> ⚠️ 이 설계는 **속으로만** 한다. 지원자에게 슬롯 표나 PSR 분해를 보여주지 않는다. 설계의 산출물은 "무엇을 어느 깊이로 물을지"에 대한 면접관 자신의 지도다.

## 1. JD 5슬롯 파싱

JD가 있으면 아래 5개 슬롯으로 쪼갠다. **JD가 없으면** 이력서의 지원 직무·경력에서 슬롯을 추론하고, `필수 기술`·`시니어리티`만 채운 채 진행한다.

| 슬롯 | 무엇을 뽑나 | 질문 설계에 쓰는 법 |
|------|------------|--------------------|
| **① 회사·도메인** | 어떤 서비스/도메인인가 (금융·커머스·인프라·데이터…) | 도메인 특유의 관심사를 질문에 심는다. 금융=정합성·멱등성·감사, 커머스=재고·동시성·정산, 트래픽=캐시·풀·확장 |
| **② 핵심 책임** | 이 사람이 매일 할 일 ("~를 설계·운영한다") | 이력서에서 이 책임을 **실제로 해본 근거**를 찾아 오프너로 삼는다. 없으면 가정 시나리오로 검증 |
| **③ 필수/우대 기술** | 반드시 쓰는 스택 + 있으면 좋은 스택 | 필수 기술 ∩ 이력서 기술 = **최우선 주제**. 우대 기술은 있으면 보너스 꼬리질문 |
| **④ 시니어리티** | 요구 연차·리드 여부 | **질문의 결**을 정한다. 주니어=정의·적용, 미들=원리·트레이드오프, 시니어=설계 판단·장애 운영. *단, **필수 도달 깊이(L1~L5)는 시니어리티가 아니라 면접 모드**가 정한다 — SKILL.md 참조. 시니어리티는 4단계 채점 가중치에도 쓰이므로 여기서 확정한다* |
| **⑤ 인재상·컬처** | 협업/오너십/성장에 대한 문구 | 클로징(2-C)의 컬처핏 질문을 이 슬롯에 맞춘다. "빠른 실행" 강조 회사면 오너십·의사결정 속도를 관찰 |

**교집합 규칙 (질문 우선순위의 뼈대):**
```
최우선   = ③필수기술 ∩ 이력서에서 본인이 주도한 경험     (그 회사가 궁금 + 검증 가능)
그다음   = ②핵심책임을 이력서 경험으로 방어할 수 있는가   (실무 시나리오로 확인)
보너스   = ①도메인 특유 관심사 + ③우대기술              (변별력용 심화)
컬처핏   = ⑤인재상 → 클로징 질문 축 선택
```

> **JD의 "우대사항"은 함정이자 기회다.** 우대 기술을 이력서에 적었다면 반드시 판다 — 진짜 쓴 건지, 이력서 채우기용인지 여기서 갈린다.

## 2. PSR 분해 (이력서 한 줄 → 질문 앵커)

이력서의 성과·프로젝트 문장을 **P(문제) · S(해결) · R(결과)** 세 조각으로 쪼갠다. 세 조각 각각이 **다른 종류의 꼬리질문**을 낳는다. 조각이 비어 있으면 **바로 그 빈칸이 첫 질문**이 된다.

| 조각 | 정의 | 이력서에 보통 어떻게 쓰였나 | 여기서 나오는 질문 |
|------|------|---------------------------|-------------------|
| **P (Problem)** | 어떤 문제/제약이 있었나 | 대개 **생략됨** ("~를 도입했다"만 있고 왜인지 없음) | "그걸 도입하기 전엔 뭐가 문제였죠? 안 하면 뭐가 터지나요?" → 문제 정의력 검증 |
| **S (Solution)** | 무엇을 어떻게 했나 | 가장 자세히 쓰여 있음 (기술명·방법) | "왜 그 방법이었나요? 대안은? 내부에서 어떻게 동작하죠?" → 기술 깊이·트레이드오프 |
| **R (Result)** | 결과가 어땠나 (숫자·영향) | "개선했다"처럼 **뭉뚱그려짐** | "몇에서 몇으로? 어떻게 측정했죠? 본인 기여는 어디까지?" → 경험 구체성 |

### 분해 → 질문 매핑 예시

이력서 문장:
> "Redis 캐싱을 도입해 상품 조회 API 응답 속도를 개선했습니다."

PSR 분해:
- **P**: (빈칸) — 왜 느렸는지, 무엇이 병목이었는지 안 쓰여 있음
- **S**: Redis 캐싱 도입 — *어떤 데이터를, 어떤 전략(cache-aside?), 왜 로컬캐시가 아니라 Redis인지* 안 쓰여 있음
- **R**: "개선" — *수치 없음*

→ 설계된 질문 흐름:
```
오프너(P 빈칸)   "캐싱을 넣기 전, 그 조회는 왜 느렸나요? 병목이 어디였죠?"
S 파고들기        "왜 로컬 캐시가 아니라 Redis였나요? 네트워크 홉이 하나 느는데요."
S 내부기작        "어떤 자료구조로 담으셨어요? Redis가 그 조회를 빠르게 만드는 이유는요?"
R 정량화          "'개선'을 숫자로 하면요? p99 기준 몇에서 몇으로, 어떻게 측정했죠?"
R 기여 구분        "그 작업, 본인이 어디까지 하셨어요? 팀이 한 건 뭐고요?"
```

> **핵심: P와 R의 빈칸이 가장 좋은 오프너다.** 지원자가 이력서에 안 쓴 조각을 물으면, 준비된 대본이 아니라 실제 이해가 드러난다. S는 이미 자세히 준비돼 있으므로, S는 "왜/내부기작/대안"으로 한 겹 더 벗겨야 변별이 된다.
>
> **PSR 밖의 빈칸 — 결여(안 한 것).** 이력서에 *없는 것*도 앵커다. "캐싱은 했는데 장애 시 폴백은 없다", "연동 대신 수작업 CSV로 처리했다", "모니터링 언급이 없다" — 이런 결여는 "왜 안 하셨어요?"(L2) 질문을 낳는다. 실제 토스 계열 면접 기록에서도 "그건 왜 안 하셨어요?"가 답이 확정될 때까지 반복되는 장면이 여러 번 나왔다.

### PSR로 "지어낸 성과" 걸러내기
- R의 숫자를 캐물었을 때 **측정 방법을 못 대거나**, P(문제)를 물었을 때 **왜 그게 문제였는지 설명 못 하면** → 남의 성과를 옮겨 적었을 신호. 압박 모드 꼬리물기의 `실제 vs 가정 구분 요구`·`정량·측정 검증` 기법으로 확인한다.

## 3. 트리거 찾기 → 프로젝트 × 소주제

실제 토스 계열 면접은 기술 키워드를 옮겨 다니지 않고, **이력서의 프로젝트 1~3개를 골라 그 안의 여러 소주제를 길게** 판다. 소주제는 아래 **트리거**에서 나온다. 관찰 기반으로 추정한 강도 순이다(근거와 예시는 `toss-patterns.md` §4).

| 트리거 | 이력서의 모습 | 소주제의 오프너 |
|---|---|---|
| **수치 주장** | 응답 속도 개선, 폴링 주기, 서버 대수, 처리량 | "어떻게 측정했나요?" "그 수치가 사용자에게는 어떤 영향이죠?" |
| **결여·미구현** | 안 한 연동, 없는 모니터링, 폴백 없음 | "그건 왜 안 하셨어요?" |
| **본인이 만든 용어** | 직접 이름 붙인 방식·구조 | "정확히 어떤 의미인가요?" → 표준 대안과 비교 |
| **정합성 장치·"보장" 문장** | 중복 방지, 정합성 보장, 트랜잭션 분리, 보상, 아웃박스, 멱등 키 | "데이터가 갱신되는 순서를 처음부터 설명해 주세요" → 실패 질문으로 |
| **장애 해결 서사** | OOM, 리밸런싱, 커넥션 풀 고갈 | "그게 원인이라는 증거는요?" |
| 기술 키워드 | Redis, Kafka, 서킷브레이커 | "어떤 자료구조/라이브러리로요?" → 원리 |
| 주도·단독 표현 | "설계했다", "주도했다" | "어디까지가 본인 몫이죠?" (소주제가 아니라 프로젝트당 1회 섞는다) |

**쪼개는 법:**
- **프로젝트를 먼저 고른다.** JD 필수기술 ∩ 본인 주도 경험이 가장 많이 걸린 프로젝트부터. JD가 없으면 이력서에서 가장 비중 있게 쓴 프로젝트부터.
- **한 프로젝트 안의 트리거 하나 = 소주제 하나.** 같은 프로젝트에서 수치 주장 하나, "보장" 문장 하나, 결여 하나가 각각 다른 소주제가 된다.
- **정합성 장치·"보장" 문장은 최소 하나 올린다.** 실제 토스 계열 면접 질문의 약 1/3이 정합성·멱등성·동시성이었다.
- **흔한 키워드는 범위로 판다.** 아웃박스·분산 락처럼 많은 지원자가 쓰는 키워드는 정의가 아니라 "유실·중복을 어디서 어떻게, 어디까지 다뤘나"로 소주제를 잡는다.
- **"어려웠다"는 기준으로 확인한다.** 원인 불명확(가설·검증 반복) / 재현 어려움 / 도구 직접 제작 / 영향 범위 / 드문 경험 중 무엇이었는지 묻는다.

## 4. 설계 산출물 (속으로 만드는 프로젝트 지도)

프로젝트마다 아래를 속으로 정리하고 2단계 진행에 쓴다. **지원자에게 보여주지 않는다.**

소주제를 고른 뒤에는 반드시 `depth-ladder.md`에서 그 주제의 카드를 읽어 **L3·L4·L5 재료와 대안을 미리 채운다.** 이 칸이 비어 있으면 면접 중에 "장애 나면요?" 같은 필러로 개수만 채우게 된다.

```
프로젝트: {예: 상품 조회 성능 개선}
- JD 근거: ③필수기술(Redis) ∩ 이력서 주도경험  → 최우선 프로젝트
- 기여 확인 포인트: "도입했다"의 범위 — 설계·구현·운영 중 어디까지 본인 몫인가
- 가정 주입 후보: 서버가 두 대로 / 은행 수준 정합성 / 동시 요청 100배일 때 정합성을 지키면서 어디가 먼저 막히나(계층별)
- 사용자 영향 질문 후보: 캐시가 stale일 때 사용자는 무엇을 보나

소주제 A: {Redis 캐싱 도입}      · 트리거: 수치 주장("응답 속도 개선")
- PSR 빈칸: P(왜 느렸나) 없음, R(수치) 없음     → 여기부터 연다
- 오프너: "캐싱 전엔 그 조회가 왜 느렸죠?"      (L1~L2)
- 사실·경계 고정: 어떤 데이터를 / 어떤 자료구조로 / TTL은 얼마로
- 필수 도달: L3 (표준 모드) / 여유되면 L4
- 대안 카드: 로컬 캐시 / 쿼리·인덱스 개선 / 읽기 복제본
- L3 재료: 단일 스레드 커맨드 처리, 자료구조 선택 비용, 직렬화, TTL 만료 방식
- L4 재료: stampede, hot key, big key 블로킹, 복제 지연 stale read
- L5 재료: 정합성 요구가 오르면 캐시를 유지할 것인가
- R 검증: 수치·측정 방법·본인 기여 (어느 층에서든 섞어 넣는다)

소주제 B: {캐시-DB 정합성}       · 트리거: "보장" 문장("최신 데이터 보장")
- 실패 → 2단 실패: 무효화 메시지 실패 → 그 재시도마저 실패하면
소주제 C: {Redis 장애 시 동작}   · 트리거: 결여("폴백 없음")
```

이 지도는 **계획일 뿐**이다. 실제 꼬리질문은 지원자의 답변에서 실시간으로 만든다 (SKILL.md의 압박 모드 규칙). **JD 슬롯·PSR·트리거는 "어디를 겨눌지", `depth-ladder.md`는 "얼마나 아래로 갈 수 있는지", `toss-patterns.md`는 "어떤 경로로 파고드는지", 지원자의 답변은 "어떻게 팔지"를 준다.**
