# 토스식 면접 패턴 (관찰 기반 레퍼런스)

이 파일은 세 스킬(mock-interview · interview-prep · interview-retro)이 함께 읽는 **토스 계열 서버/백엔드 면접에서 관찰된 경향**이다. 질문을 "어떻게 이어 가는지"(꼬리질문 단계·면접관 행동)와 "무엇을 좋게/나쁘게 보는지"(평가 신호)를 담는다.

- `question-design-guide.md`는 **어디를 물을지**, `depth-ladder.md`는 **얼마나 아래까지 팔 수 있는지**, 이 파일은 **실제 토스 계열 면접관이 어떤 경로·태도로 파고드는지**를 준다.

> **출처와 한계 — 반드시 지킨다.**
> - 출처: 토스 계열사(뱅크·증권·플레이스 등) 서버/백엔드 면접 기록 5건(면접관 질문 약 245개)과, 토스 서버 개발자 채용 담당자가 진행한 채용 세션(러너스 하이) 녹취를 분석해 **일반화한 것**이다. 원문·개인정보는 담지 않는다.
> - 면접 기록 중 일부는 사전·모의 인터뷰이고, 답변 평가는 대부분 **복기 작성자의 분석**이지 면접관의 공식 채점이 아니다. 채용 세션의 일부 사례는 한 조직(Q&A 답변자의 팀) 사례다.
> - 그래서 아래는 **"토스 규정"이 아니라 "관찰된 경향"**이다. 지원자에게 "토스는 반드시 이걸 묻는다"라고 말하지 않는다. 수치는 대략의 비중으로만 쓴다.
> - 계열사·라운드별 차이는 표본이 작고 질문이 지원자 이력서를 따라가서 **구분할 수 없다.**

---

## 1. 한 줄 요약

이력서에 쓴 것에서 출발해 → **사실·경계를 고정**하고 → 조건을 바꿔 가며 → **정합성·실패 상황**으로 파고들고 → **근거(관측·측정)와 한계**까지 확인한다. "말하게 하는" 면접이 아니라 **"확인하고 따지는"** 면접이다.

## 2. 질문 분포 (경향)

| 질문 기능 | 대략 비중 | 예 (일반화) |
|---|---|---|
| **사실·경계 확인** | **가장 많음 (약 1/4~1/3)** | "폴링 주기는 얼마로 설정돼 있나요?" / "같은 트랜잭션인가요, 서비스 간 호출인가요?" |
| 선택 이유·대안 | 약 10~15% | "로컬 이벤트 리스너로도 되지 않나요?" / "그걸 안 하신 이유가 있나요?" |
| 실패·장애 시나리오 | 약 10~15% | "외부 호출은 성공했는데 우리 DB 커밋이 실패하면요?" |
| CS·내부 원리 (앞 답에서 파생) | 약 10~15% | "UPDATE만으로도 락이 걸리나요? 어디에요?" |
| 열린 서술형 | 약 5% | "어떤 경험이 있으세요?" |

- 주제 축으로 보면 **정합성·멱등성·동시성 관련이 약 1/3**이다(기록에 따라 1/4~1/2). 채용 세션 발표자도 "정합성을 많이 본다"고 말했다.
- **CS 질문은 관찰된 기록에서 대부분 앞 답변·이력서 키워드에서 파생됐다**(예: 장애 서사 → 그 메모리 영역, 중복 방지 → 유니크 제약의 내부 구현). 독립된 CS 퀴즈 형태는 거의 보이지 않았다.
- 표본이 기술·직무 면접이라 컬처핏 질문은 관찰되지 않았다. **토스가 컬처핏을 묻지 않는다는 근거가 아니다.**

## 3. 꼬리질문 단계 메뉴 (고정 순서 아님)

한 소주제를 팔 때 아래 단계에서 **골라** 쓴다. 순서는 지원자 답에 따라 바뀌고, 모든 단계를 다 밟는 체인은 드물다. 오른쪽 열은 우리 깊이 레벨(L1~L5)과의 대응이다.

| # | 단계 | 형태 | 예 (일반화) | 레벨 |
|---|---|---|---|---|
| 1 | 진입 | 경험·구조 설명 요청 | "그 처리 흐름을 처음부터 설명해 주세요." | L1 |
| 2 | **사실·경계 고정** | 설정값·구성·경계를 이분법으로 확정. 흐리면 표현을 바꿔 재질문, "~인 거죠?"로 요약 확인 | "그 두 처리는 같은 트랜잭션인가요, API 호출인가요?" "그럼 요청마다 키가 새로 만들어지는 거죠?" | L1 |
| 3 | **왜 + 대안** | 면접관이 대안 이름을 직접 댐 / 안 한 것을 물음 | "CDC는 검토하셨어요?" "Sorted Set으로 하지 않은 이유는요?" | L2 |
| 4 | **실패** | 단계 사이 실패 · 동시 요청 · 중복 요청 · 응답 유실 · 지연 | "응답을 클라이언트가 못 받으면요?" "마지막 1개에 두 요청이 동시에 오면요?" | L4 |
| 5 | **2단 실패** | 실패를 처리하는 장치 자체의 실패 | "그 보상(취소) 처리마저 실패하면요?" | L4 |
| 6 | **허점·모순 지적** | 앞 답 인용 / 이해가 안 되면 그 자리에서 말함 / 허점을 짚고 바로 해결을 물음 | "아까는 ~라고 하셨는데요." "이 쿼리가 잘 이해가 안 돼요." | (L2~L4) |
| 7 | 개선안 | 고칠 방법, 근본 해결 | "근본적으로 해결하려면요?" | L5 |
| 8 | **조건 강화** | 도메인 강화 · 인스턴스 증가 · 트래픽 · 신뢰 경계 변경 | "은행 수준으로 중요한 데이터라면요?" "서버가 두 대로 늘면요?" "10만 명이 동시에 요청하면, 정합성을 지키면서 어디가 먼저 막히죠?" "클라이언트를 신뢰하지 않는다면요?" | L5 (일부 L4) |
| 9 | **단순화 / 구체화** | "꼭 필요한가요? 더 간단히는?" / 키·값, SQL 순서, 의사코드 | "서킷브레이커 없이 간단히 할 방법은요?" "실행될 SQL을 순서대로 써 주실래요?" | L2·L5 / L3 |
| 10 | **원리 하강 (CS)** | 방금 나온 기술의 내부 동작, "직접 구현한다면?" | "유니크 제약을 스토리지 엔진에서 직접 구현한다면요?" | L3 |
| 11 | 앞 소주제와 비교 | 앞에서 나온 해법과 같은 점·다른 점 | "앞의 조건부 UPDATE와 지금 것은 뭐가 같고 다르죠?" | L5 |

- **원리(L3)는 구체적인 실패 질문 직후나 체인 끝에 오는 경우가 많다.** 구체적인 실패 상황을 던지고 "그때 내부에서는 무슨 일이 일어나죠?"로 내려간다. 다만 원리가 먼저 오는 체인도 있다 — **경향이지 규칙이 아니다.**
- 확장성 질문은 **구체 수치 + 어디가 먼저 터지나 + 계층별로 + 지켜야 할 조건**("정합성을 유지하면서")이 붙은 형태로 나온다. 이 조건이 빠진 "트래픽 10배면요?"는 필러다.

**단계 태그 (세 스킬 공통 — 세션 노트·리포트·회고에서 이 이름 그대로 쓴다):** `진입` · `사실·경계 고정` · `왜+대안` · `실패` · `2단 실패` · `허점 지적` · `개선안` · `조건 강화` · `단순화` · `구체화` · `원리 하강` · `비교` · `기여 확인` · `사용자 영향` · `조건 확인(지원자)` — 마지막 셋은 위 표 밖의 보조 태그다(기여 범위 질문, 사용자 영향 질문, 지원자가 요구·조건을 되물은 장면).

## 4. 질문이 시작되는 이력서 지점 (트리거)

관찰 기반으로 추정한 강도 순이다(정량 순위가 아니다). 1단계 설계에서 소주제(갈래)를 뽑을 때 쓴다.

| 트리거 | 이력서의 모습 | 첫 질문 형태 |
|---|---|---|
| **수치 주장** | 응답 속도 개선, 폴링 주기, 서버 대수, 처리량 | "어떻게 측정했나요?" "초당인가요?" "그 수치가 사용자에게는 어떤 영향이죠?" |
| **결여·미구현** | 안 한 연동, 없는 모니터링, 폴백 없음 | "왜 안 하셨어요?" (답이 확정될 때까지 재질문) |
| **본인이 만든 용어** | 직접 이름 붙인 방식·구조 | "정확히 어떤 의미인가요?" → 표준 대안과 비교 |
| **정합성 장치·"보장" 문장** | 중복 방지, 정합성 보장, 트랜잭션 분리, 보상, Outbox, 멱등 키, 대사 | "데이터가 갱신되는 순서를 자세히요" → 실패 질문으로 |
| **장애 해결 서사** | OOM, 리밸런싱, 커넥션 풀 고갈 | "원인이라는 증거는요?" "어느 구간의 메모리죠?" |
| 기술 키워드 | Redis, Kafka, 서킷브레이커 | "어떤 자료구조/라이브러리로요?" → 원리 |
| 주도·단독 표현 | "설계했다", "주도했다" | "직접 주도하셨나요? 어디까지가 본인 몫이죠?" |
| 이력서 인접 기능 | 해 본 적 없는 비슷한 기능 | "그런 기능도 해 보셨어요?" → 가상 설계 |

- **흔한 키워드는 정의가 아니라 다룬 범위를 묻는다.** 채용 세션 발표자는 그 세션 제출자의 약 30%가 Outbox로 정합성을 맞춘 사례를 적었다고 관찰했다. 키워드만으로는 차별화가 어려우니, **유실·중복을 실제로 어떻게 다뤘는지, 어디까지 다뤘는지**를 묻는다.
- **"어려웠다"는 주장은 기준으로 확인한다.** 발표자가 든 판단 요소: 원인이 불명확해 가설·검증을 반복했나 / 간헐적이라 재현이 어려웠나 / 도구가 없어 직접 만들었나 / 영향 범위(팀↔회사 전체, 프로젝트 일부↔전체) / 드문 경험인가. 안 되던 것을 되게 하면서 여러 조건까지 처리할수록 어렵다고 본다.
- **비동기·스레드 위임 구조는 생명주기 경계를 묻는다.** 발표자가 면접에서 물어볼 만하다고 직접 든 유일한 예가, 처리를 다른 스레드에 넘기는 컨슈머 구조에서 **서버가 내려갈 때 넘어간 레코드와 커밋을 어떻게 처리하는가**였다.

## 5. 면접관 행동

| 행동 | 형태 |
|---|---|
| **사실 고정 후 허점 공격** | "결국 ~인 거죠?"로 요약 확인 → 그 전제의 빈틈으로 바로 이어 감 |
| **표현만 바꿔 재질문** | 경계·이유 질문에 답이 흐리면 확정될 때까지 (3~4회도 있음) |
| **모순 인용** | 앞 답을 기억해 "아까는 ~라고 하셨는데요" |
| **이해가 안 되면 즉시 신호** | "이 부분이 잘 이해가 안 돼요" — 설명이 막힌 지점에서 바로 |
| **대안 직접 제시 · 단순화 요구** | "다른 방법은?"이 아니라 구체 대안을 댐. 복잡한 해법엔 "꼭 필요한가요? 더 간단히는?" |
| **가정 주입** | 프로젝트마다 조건을 바꿔 다시 묻는다 |
| **관측 근거·설정값 요구** | "어떻게 아셨어요?" "정확히 몇 개죠?" — 결론이 맞아도 근거를 못 대면 계속 파고든다 |
| **기여 범위 확인** | "직접 주도하셨나요?" "그 부분은 직접 구현하신 건 아니죠?" |
| **현재 구현 vs 개선안 분리** | 현재 구현을 물었는데 개선안으로 답하면 같은 질문을 다시 한다 |
| **모르면 추측 요구** | "직접 안 하셨다면, 왜 그랬을 것 같으세요?" — 이유뿐 아니라 방식·수치도 추측시킨다 |
| **막히면 최소 힌트** | 조각 하나만 주거나 한 칸 쉬운 유추 질문으로 유도한 뒤 다시 파고든다 |
| **조건 되묻기 허용** | 지원자가 "한 사람당 한 개 조건인가요?"처럼 요구를 확인하면 답해 준다 (요구 확인은 긍정 신호) |
| **사용자 영향 환기** | "그때 고객은 무엇을 경험하나요?" |
| 면접 중 평가 | **점수·정답 여부는 말하지 않는다.** 다만 허점 지적, 힌트, "이해가 안 된다"는 신호는 준다 |

톤: 적대적이지 않지만, **확인이 끝날 때까지 다음으로 넘어가지 않는다.**

## 6. 가상(라이브) 설계

- 관찰: 2차 직무 인터뷰에서 이력서와 같은 동시성 원리를 쓰는 **고전 문제**(예: 선착순 한정 수량 발급)를 라이브로 설계시켰다. 다른 기록에도 "이 이벤트가 재전달돼도 한 번만 반영하려면?"처럼 말로 설계하게 하는 가상 시나리오가 있다.
- 흐름 예: 경험 확인("해 보셨어요?") → 요구·조건 명확화(지원자의 확인 질문 허용) → 테이블 설계 → 한 요청에서 실행될 SQL 순서 → 마지막 1개에 동시 2요청 → 락 원리 → 중간 단계 실패 → 중복 요청 → 순서 뒤집기 → 대규모 동시 요청(정합성 유지 조건) → 이력서의 비슷한 해법과 비교.

## 7. 평가 신호

### 7-1. 채용 세션(러너스 하이)에서 발표자가 말한 것

- 발표자는 면접을 **이력서를 바탕으로 한 개발자 간의 기술 대화**로 설명했다. 보는 것은 **적용한 기술을 얼마나 이해했고, 얼마나 잘 설명할 수 있는가**.
- **이해도가 뿌리다.** 이해도가 높으면 설명이 논리적·간결해지고, 이력서와 일관되며, 더 깊은 원인·근거까지 답한다. 이해도가 낮으면 질문 의도를 파악하는 데부터 시간이 걸린다. *(2차 정리 자료는 이를 "기술 이해도 부족 / 이력서와 다른 답변 / 얕은 문제 해결 / 장황한 설명" 네 가지 피드백으로 요약했다 — 슬라이드 기반이라 직접 확인은 못 함.)*
- **판단 주체**: 다른 사람(예: 그 회사 시니어)이 시켜서 한 일이라면 토스에서도 같은 일을 해낼지 알 수 없다. 접근 방식, 어떤 지표를 보고 무엇을 판단했는지를 본다.
- **기술 도입 근거**: "새롭고 좋아서"가 아니라, 지표를 보고 다른 선택지와 비교·검증했는가. (Q&A 답변자 팀 사례: 모니터링으로 이상을 보고 프로파일링으로 비용 구간을 찾은 뒤 대안을 실측해 선택했고, 성능과 관리 부담을 함께 보고 다른 대안을 버렸다.)
- **다음 단계**: "내가 이 팀을 이끈다면 다음에 무엇을 하겠다"를 그릴 수 있는가 — 주도성과 이해 깊이의 신호.
- **한계와 계획**: 구현하지 못했더라도 고민한 방향, 시스템의 한계와 처리 방안을 말할 수 있으면 좋게 본다. 실제로 해 본 것이 있으면 더 좋다.
- **정합성**: 락·트랜잭션·인덱스·Outbox·메시지 유실과 중복을 어떻게 다뤘는지를 많이 본다.
- **학습 능력**: 모든 걸 가르쳐야 하는 사람 → 키워드·방향을 주면 하는 사람 → 재료만 줘도 스스로 학습하는 사람 순으로 높게 본다(온보딩 비용 판단).
- **시간 밀도**: 연차에 걸맞은 성과를 꾸준히 냈는가. 발표자는 면접 탈락 사유로 "경력 대비 역량 부족"이 가장 많다고 말했다.
- **트래픽**: 대규모 트래픽 경험이 없다는 이유만으로 배제하지 않는다(Q&A 답변자). 자동화·빌드·테스트·운영 개선으로도 역량을 보일 수 있다.

### 7-2. 면접 기록(복기)에서 드러난 신호 — 대부분 복기 작성자의 분석, 공식 채점 아님

- (+) **요구를 먼저 확인**한다 — "원자성이 정말 필요한가요?"처럼 되물어 범위를 좁힌다.
- (+) **추정과 확증을 구분**하고 과장하지 않는다 — 구현하지 않은 것은 안 했다고 말한다.
- (+) **가장 간결한 원자적 해법**을 짚는다 — 고유 ID + 유니크 제약 + 같은 DB 트랜잭션, 조건부 UPDATE 등. (복잡한 해법을 말하면 면접관이 최소 설계를 다시 요구하는 장면이 여러 기록에 있다.)
- (+) 모든 문제에 무거운 도구(메시지 큐·분산 트랜잭션)를 넣지 않는 **비용 판단**.
- (−) 장애 원인을 **로그·지표 증거로 입증하지 못함** — "큰 감점 후보". 증거가 없으면 "유력 가설 + 검증 방법"으로 말해야 한다.
- (−) **현재 구현과 개선안을 섞음** → 면접관이 같은 질문을 반복했다.
- (−) **서로 다른 저장소·외부 호출에 걸친 원자성을 오해** — 예: 캐시 서버의 스크립트로 DB 변경까지 원자화된다고 봄, 트랜잭션 안에서 외부 HTTP를 호출하면 정합성이 지켜진다고 봄.
- (−) 설정 수치를 바로 대지 못함, 본인 기여와 측정 결과가 흐림, 배경이 길고 AS-IS/TO-BE가 섞임.
- 면접관 조언(한 기록): 넓은 시야로 요구사항을 보고 **다양한 시나리오와 트레이드오프를 충분히 검토한 뒤** 설계 결정을 내리는 습관.

### 7-3. 좋은 답변의 골격 (위 신호를 종합한 권장 구조)

1. **전제·요구 재확인** — 필요하면 되묻는다.
2. **현재 구현을 한 문장으로** — 수치·증거를 붙이고, 모르는 것은 "가설"로 표시한다.
3. **선택 근거와 버린 대안**, 그 비용.
4. **실패 경로와 남은 위험·한계**를 먼저 인정한다.
5. **개선안은 가장 단순한 해법부터.**
6. **사용자 영향과 운영**(감지·대사·복구)으로 마무리.

> 모든 답이 6단계를 다 가질 필요는 없다. 질문이 묻는 층에 맞춰 필요한 칸만 쓴다. 다만 **2번(현재)과 5번(개선)을 섞지 않는 것**은 항상 지킨다.

## 8. 스킬별 사용법

- **mock-interview** — 1단계 설계에서 §4 트리거로 소주제를 뽑고, 2단계에서 §3 단계 메뉴와 §5 행동으로 꼬리질문한다. 1시간 심화 모드의 가상 설계는 §6. 개선안·채점 관점은 §7.
- **interview-prep** — 갈래를 §4 트리거에서 뽑고, 갈래 안의 예상 질문을 §3 단계로 펼친다. 답변 골격은 §7-3.
- **interview-retro** — 실전 질문을 §3 단계로 태깅해 **어느 단계에서 끊겼는지** 보고, 지원자가 적어 준 답변 체감을 §7-2 신호에 비춰 본다.
